## 2. 根因修复：SGSR1 从未真正加载（SHD-02 真实 FAIL 的根因）

brief-v2 记录的 SHD-02 现象（chain_verified=true 但 fresh DESC 不在场）的根因**不是**
fresh/redraw 检测缺陷，而是 shader 文件在 mpv 0.40-393 / libplacebo v7.357 上解析失败：

- 实测证据（隔离环境）：mpv 日志报 `[e][vo/gpu-next/libplacebo] Missing variable type!`
  + `Failed to parse user shader`，随后 `Registering hook pass` 从未出现，
  vo-passes 全程只有 mpv 内建 pass（bicubic 等）。
- 二分定位：注释行中的指令样文字（`//!PARAM` / `//!WHEN` 字样出现在 `//` 注释中间）
  被解析器误当作真实指令，注入伪 `//!PARAM` 块后因缺少 `//!TYPE` 报
  "Missing variable type!" 并拒载整文件。基文件 `docs/证据/port-SGSR.glsl` 原文即带
  此写法，非本阶段改坏。
- 修复：仅将头部注释内的此类文字去前缀（`!PARAM`/`!WHEN`），真实指令行与算法零改动；
  修复后实测 `Registering hook pass: Snapdragon Game Super Resolution (GSR) v1` 出现，
  vo-passes 中该 pass 实际运行。
- FSR1 头部注释含同类文字（`//!WHEN`/`//!WIDTH///!HEIGHT`），修复前能加载属侥幸
  （其注释无 `//!PARAM` 字样，注入的伪 WHEN 未触发致命分支）；一并消除隐患。
- 检测增强照做（brief 要求）：验证器新增帧新鲜度证明（§4），但"检测"不再是失败根因。

## 3. SHD-03（Nearest）真实基线 oracle

brief-v2 记录的 SHD-03 FAIL 根因是旧验证草稿假定 Off 后三核全为 bicubic；实测本机
mpv 0.40 默认为 `scale=bicubic, cscale=bicubic, dscale=hermite`。现行为：

- 激活前由 Lua `take_snapshot` 采集真实基线并经 `user-data/scale-selector/baseline`
  导出；Off 恢复后逐 property 与该快照比较（cscale 缺省跟随 scale 的规范化在案）。
- 不把默认核强改成 bicubic 凑过；默认验证基线即本机真实默认
  （high-quality 场景下用户自设值同样按快照恢复）。测试草稿的 `off_restores_bicubic`
  假设已废弃，不进最终矩阵。

## 4. 帧新鲜度证明（fresh/redraw/帧 epoch，数据互斥）

`tools/p2_verify.py` 新增 `fresh_pass_proof`：激活并 `chain_verified=true` 后，
间隔 ≥0.8s 取两份 vo-passes 样本，要求：

1. 后一样本中本链 `//!DESC` 关键字在场（pass 现在存在）；
2. 两样本间渲染 pass 帧计数严格递增（证明帧在流动——命中不可能来自激活前冻结的旧帧，
   数据互斥：陈旧帧不得报 active）；
3. 命中 pass 的 `samples` 非空（真实 GPU 计时在案）；
4. 证明窗口内 `chain_epoch` 不变（证据属于当前代，无中途重建）。

SHD-01/SHD-02 主变体的实测样本计数（228→361 / 223→343）见 full-r2 objective-results。
Lua 侧的 paused/redraw 语义（暂停时 fresh 冻结、redraw 仍可作为合法在场证据）
保持 brief-v1 决策不变，由 WINDOW-01 的 pause+resize 步骤覆盖。

## 5. 1080p→1440p 真目标 2560x1440（窗口 vs 纹理 vs 截图分辨）

- 本机显示器 2560x1440（mpv 日志 `monitor size: 2560x1440`）。旧调试用窗口 1.5× 被
  WM 钳制到 2496x1404，不满足主场景要求。现 SHD-01/SHD-02 主变体改为**全屏**：
  `osd-dimensions` 实测 2560x1440，即真实输出矩形/纹理目标。
- 三类尺寸严格分 field 记录：`true_output_texture_target`（2560x1440）、
  `dw/dh`（1920x1080，仅显示比例参数，`ratio_from_dw_dh==1.0` 明示）、
  截图（窗口捕获，`screenshot_is_capture_not_texture=true`）。
- FSR 的每轴 ≤2× 钳制在此目标下真实生效（2560<3840、1440<2160 → FSR 全权接管）。

## 6. SHD-13（编译失败/缺资源回退）真实失败条件与语义在案

- 负例构造修正：必须在 >1× 窗口先成立，损坏 shader 才会真正走到编译/验证失败
  （≤1× 时 `//!WHEN` 合法跳过，SHD-01/02-b 变体已证明该跳过是合法行为）。
  现两变体先 `current-window-scale=1.5`（等待真实帧渲染后再设）再激活损坏档位。
- 语义记录（不改状态机凑测试）：P1 继承的状态机在激活时即置 `stable=当前档位`，
  故首次验证失败走 `release_all_to_fallback` 分支——整体释放回 off、缩放核恢复
  接管前真实基线（逐 property 比对快照）、glsl-shaders 恢复为空、无损坏残留、
  reason 明示"链验证失败（缺失: …）"。"重放上一稳定档"分支代码保留但在首次失败
  流程下不可达；按 brief-v1"编译失败回退沿用 P1 状态机"，不为凑测试改状态机。
  此语义差异已在本文件记录，供下游独立审查裁量。
- 缺资源负例（variant c）：fallback reason 明示 `shader 文件缺失: ~~/shaders/p2-SGSR1.glsl`。
