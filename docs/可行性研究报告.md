# 截图中的缩放算法接入 mpv：可行性研究

> 日期：2026-10-02。范围：原生 mpv 菜单与视频缩放，不含帧生成器重写。
> 图片：`C:/Users/kkiw/Pictures/Snipaste_2026-10-02_20-23-55.jpg`。
> 本报告是整合后的结论；`研究素材/` 中早期初稿不是验收依据，勘误见 [勘误说明](勘误说明.md)。交叉审查的候选指纹及结果见 `交叉审查/`。

## 0. 结论

**做成 mpv 内部的“缩放算法选择器”总体可行，无须修改 mpv 本体。** 截图十种方法中，八项有明确的实现路线：FSR1、NIS、SGSR1、Anime4K、xBR、Sharp Bilinear、Integer、Nearest Neighbor。FSR1/NIS/SGSR1 已找到可读取源码的 mpv 适配版；Anime4K 本来就支持 mpv，且本机已有资产。

**LS1 暂不能承诺原样内置**：官方确认为小型神经网络，但未取得公开源码、权重和移植许可。**BCAS 的准确算法定义尚未核实**；可以另做有明确名称的 CAS 或“Bicubic + CAS”候选，不能冒充截图中的 BCAS。

工程可行不等于画质必然提升，也不等于与 Lossless Scaling 逐像素一致。建议先做 SDR 小型验证包，保留你偏好的 stock Anime4K，与现有高质量传统缩放器进行公平比较，再决定默认档。

## 3. 为什么无需改 mpv 内核

### 首选：Lua 控制层 + 原生缩放/用户着色器

大致流程是：解码与现有 RIFE vf → 视频纹理 → 一种选定的空间缩放方案 → mpv 后续颜色管理/输出。具体插入位置必须与 shader 的颜色域匹配；并非所有算法都能放在同一 hook。

- Lua 用 `mp.set_property_native("glsl-shaders", list)` 或 `change-list` 切换 shader 列表；内建档切换 scale 与必要的显示几何。
- `LUMA` 适用于确有亮度平面的输入；`MAIN` 是转成 RGB 后、主缩放之前的可变尺寸图像。RGB 源不保证触发 LUMA，因此亮度 port 必须检测输入格式并回退，或另做 RGB 适配。
- `//!HOOK`、`BIND`、`SAVE` 表达同帧多 pass；`WIDTH/HEIGHT` 指定输出纹理尺寸，`WHEN` 控制执行条件。
- **只有 resizable hook 可以变尺寸**。不能在固定 `OUTPUT` 点写不同宽高；也不建议从 OUTPUT 重新采 MAIN 替换成最终图像，这可能绕过正确的颜色管理。
- shader 改尺寸时，像素如何重采样由该 shader 的采样逻辑决定，不会自动套用 scale/dscale 核。若中间尺寸不等于视频目标尺寸，后续主缩放器可能再处理；不能一概说“一定多走一次同样的缩放”。
- NIS 使用 `//!COMPUTE`；需要可用的 compute 后端。**compute 不应被笼统说成 gpu-next 专属**，但首版可只验证固定 `gpu-next` 后端，减少兼容面。
- 多 pass 的 `SAVE/BIND` 不是上一帧历史纹理接口。普通 hook 链没有现成的游戏深度/运动矢量输入，不能因此顺手引入 FSR2/3、SGSR2。
- mpv 参数用相应 user-shader `//!PARAM` 与 gpu-next 的 `glsl-shader-opts` 机制；RetroArch 的 `#pragma parameter` 不是可直接粘贴的 mpv 参数接口。部分旧 port 用 `#define`，需适配参数或使用版本化文件，不能假设已支持连续热调锐化。

### 备选：vf

本机 `vf=libplacebo` 提供 `upscaler/downscaler`、`custom_shader_path` 等选项；`vf=xbr` 提供尺度参数。它们可用于固定尺寸验证，但增加滤镜链与帧格式/设备互通的复杂度，**不能假设所有 vf 都在 CPU 跑，也不能假设 GPU vf 永远没有拷贝**。视频显示目标随窗口变化时，VO 层的方案更直接。不要为菜单切换去改现有 RIFE vf。

## 4. 逐项判断

### 4.1 FSR：做 FSR1，而不是 FSR2/3

官方 FSR1 是 EASU 边缘自适应上采样加 RCAS 锐化，MIT 许可。已读取 [agyild 的 FSR.glsl](https://gist.github.com/agyild/82219c545228d70c5604f865ce0b0ce5)：两个 `HOOK LUMA`，EASU 保存 `EASUTEX`，RCAS 读取结果。

该 port 每轴最多放大 2×（面积 4×），之后由 mpv 处理剩余尺寸；1080p→1440p 的 4/3 比例在此范围内。“4×”不能误解成每轴 4×。port 是亮度适配而非官方 RGB 逐像素复刻。

首版限定普通 SDR YUV 视频，验证锐化、噪声、色度、等尺寸/缩小/首 pass 跳过时的依赖处理。其 `FSR_PQ` 开关不是完整 HDR 支持的保证。接入与 SDR 验证估计 1–3 人日。

### 4.2 NIS：已有 NVScaler，不是 DLSS

官方 NIS SDK 是空间缩放与方向性锐化，MIT 许可，非 RTX Tensor Core 专属 AI。官方 NVScaler 已含锐化，**不要默认再叠加 NVSharpen**。

已读取 [NVScaler.glsl](https://gist.github.com/agyild/7e8951915b2bf24526a9343d951db214)：`HOOK LUMA`、`COMPUTE 32 24 256 1`、两张系数纹理，6-tap/64-phase 系数配置。不是先前猜测的“固定两 pass”。

技术重点是 compute 编译、工作组与边界写入、坐标/裁剪/旋转、纹理格式支持，以及与 RIFE 的 GPU 竞争。官方颜色域与 port 的 HDR 定义还需分别核对，不能用一个 PQ 开关覆盖全部管线。SDR 接入与验证估计 2–4 人日。

### 4.3 SGSR：高通 SGSR1，已有 mpv port

官方是 **Qualcomm Snapdragon Game Super Resolution**，不是 AMD。官方 SGSR1 为单 pass 的 12-tap Lanczos-like 上采样和自适应锐化；SGSR2 是时域方案，本研究不引入它。许可为 BSD-3-Clause。

已读取 [agyild SGSR.glsl](https://gist.github.com/agyild/7715b6b1f38427839d58f80884902cab)：一个 `HOOK LUMA`，带边缘方向、阈值、锐化参数，放大时输出目标尺寸。**作者明确将原版绿色通道依据改成了亮度通道，并做了修正/优化**；因此是 SGSR1 的视频适配版本，不承诺等于 Lossless Scaling 的 RGB 结果。

重点测试 `gather`、新式 PARAM 类型与本机构建的兼容性、0–1 钳制/色彩域，以及锐化噪声。手机版优化背景不妨碍桌面 GPU 实现。复用 port 的 SDR 接入估计 1–3 人日。

### 4.4 LS1：不把替代品冒充原版

Lossless Scaling 官方公告称 LS1 为“小而快的通用神经网络”，优化范围约 1×–2×。本轮未取得原网络架构、权重、公开源码或移植/再分发授权。

因此，**原样做成独立 mpv shader 没有足够实施依据**，而不是数学上不可能。自行训练或使用 Anime4K/其他网络都只能是另一个算法，不能标作 LS1。若必须保留原版效果，可另行使用外部 Lossless Scaling 处理 mpv 窗口，但那不是内置 mpv 插件，也不在本次部署范围内。

### 4.5 BCAS：保持身份未明，不补造定义

已读取的 Steam 商店说明和公告未给出 BCAS 的可靠全称/算法定义。仅凭 B/CAS 字母不能认定它是 Bicubic CAS、Bilinear CAS 或 Bilateral CAS。缺少截图的软件版本也是限制。

AMD CAS 本身开源，官方支持锐化及可选上采样，mpv 也已有 `CAS.glsl`/`CAS-scaled.glsl`。可以先实现明确命名的 CAS，或验证另行组合的 Bicubic + CAS。**这些候选不能证明 BCAS 同一性；原版档位须等待软件版本或权威定义补证。**

### 4.6 Anime4K：复用 stock，避免重复造轮子

官方即提供 GLSL/mpv 安装方法。本机已有 stock v4 链与快捷键；新增菜单可以把已有模式作为一个家族/子菜单，而不是再下载一套或强制改变默认模式。

工程上明确可行，但截图里的 Anime4K 版本/链未明，不能保证与 LS 中的同名选项一致。不同模式的线条重塑、降噪、锐化和 GPU 成本差异很大。保留你的 stock 偏好，将它纳入 A/B 基准；不能用旧项目的负面结论直接排除它。

### 4.7 xBR：可做，优先像素艺术

已读取 libretro `xbr-lv2.glsl` 的算法与 MIT 许可头；它使用 RetroArch 顶点/fragment 接口，不能直接作为 mpv hook 使用。选定一个版本，将邻域采样与坐标映射转成 MAIN 的单 pass，或用 SAVE/BIND 表达选定的多 pass 链即可。算法不天然需要跨帧反馈。

本机 `vf=xbr=help` 也确认有现成 FFmpeg 路线，可作为初步验证入口，但其具体算法版本与截图未必相同，CPU 成本及先放大再收尾的代价需要测量。

xBR 与 xBRZ 是相关但不同的实现，许可须按实际选用文件核验；不能把 xBRZ 的许可当成所有 xBR 的许可。适合复古游戏/像素画录像，不应默认处理平滑抗锯齿动画或实拍。GPU 移植与验证估计 2–5 人日。

### 4.8 Sharp Bilinear：简单，但必须选清楚变体

Themaister 的公开领域 shader 使用采样坐标重映射模拟整数 nearest 预缩放后的双线性缩放，可用单 pass 完成。移植时改成 mpv hook 接口，建议 MAIN 可变尺寸路径，保留后续颜色管理。

当前核对的 AUTO 变体取 `floor(output_height / input_height + 0.01)`；1080p→1440p 时得到 1，**退化成普通双线性**。手动预缩放值 2 可作为另一种明确标注的模式，但不能静默声称它就是该 AUTO 变体或 LS 的同款参数。

验证采样滤波与半像素坐标、低分辨率棋盘格、运动细线；不要保证像素闪烁会完全消失。估计 0.5–2 人日。

### 4.9 Integer：显示策略，不是超分网络

在方形像素、无旋转裁剪、正常等比显示的简单场景：

`k = floor(min(可用宽/源宽, 可用高/源高))`

用 `video-unscaled=yes`、`video-zoom=log2(k)` 和 nearest 实现整数倍显示；k<1 时回退正常缩小，而不是裁掉画面。实际脚本必须依据 vf 之后的有效显示尺寸与窗口像素尺寸，不可只读取解码前的 width/height；SAR、DPI、旋转、窗口变化与整数坐标对齐需测。

1080p 的 1920×1080 在 2560×1440 屏只能取 1×：左右各 320px、上下各 180px 黑边。720p 的 1280×720 则可 2× 满屏。**整数倍本身不会让 Lanczos 变成像素复制；要求严格像素块须使用 nearest。** 接入、恢复状态与几何边界验证估计 1–2 人日。

### 4.10 Nearest Neighbor：直接用内建核

设置 `scale=nearest` 即可，无需另造 GLSL。原生支持不代表适合所有视频：1.333× 时像素宽度不均、锯齿与运动闪烁通常更明显。

要明确 cscale 选择：本构建的文档说明 cscale 未设时跟随 scale；普通视频档宜保留/固定合适的色度缩放，真正像素模式再决定是否同步 nearest。缩小策略 dscale 与时域 interpolation/RIFE 不应随意联动；nearest 的空间选择不是“必须关插帧”。

## 5. 最小实施路线

### 第一阶段：证明管线与切换可靠

先做 `关/原配置`、stock Anime4K、FSR1、SGSR1、Nearest 对照，范围限定 SDR YUV、1080p→1440p，显式固定 GPU 后端。原型预估 3–6 人日，**不是交付承诺**。

Lua 菜单只负责选择一种空间缩放链、显示实际生效状态与回退原因。菜单可用 F8 一键打开，不必为十项挤占十个快捷键；保留 CTRL+1…6、F7 RIFE。锐化参数按算法适配，不能机械映射同一数值。

### 第二阶段：NIS 与边界场景

验证 NIS compute；补充 720p/4K、窗口缩放、RGB 输入、尺寸不变/缩小、裁剪旋转与整数几何。HDR 单独立项，在证实前不自动启用这些 SDR port。

### 第三阶段：像素风工具

增加 Sharp Bilinear 与选定 xBR 版本；整数缩放用于其合适场景。BCAS 保持未核实或明确展示替代名称；LS1 保持不可用说明。首版不训练新网络，也不重写已有 RIFE。

单人完成八项基本选择器加 SDR 边界验证，粗估 1–3 周或更久；多个图形后端、HDR 和完整画质评估会增加工作量。

### 配置与状态所有权

- 一次只选一种主缩放链；**FSR/NIS/SGSR 不应继续无脑 append 到现有 Anime4K 链后**。
- “关”恢复接管前的 baseline；不使用 `glsl-shaders-clr` 粗暴删除所有用户 shader，也不把“关”理解成关闭 mpv 必需的缩放/色彩管理。
- 管理并恢复 glsl-shaders、scale/cscale/dscale 及本插件改变的显示几何。保留兼容的无关效果；不可把外部已经修改的状态用陈旧快照覆盖。
- 检测用户 CTRL+1…6 或其他脚本从外部改链后，标记“外部模式”并让出控制，避免两个脚本互相覆盖。
- 缺 shader、格式不适配、编译失败或 WHEN 跳过时显示真实状态并回退；不要菜单显示“FSR”但实际只在用内建 scaler。
- 首版用独立配置目录/命令行验证；安装与卸载采用可识别的管理范围，测试成功并获用户同意后再接入活动配置。

## 6. 验证门槛与尚未验证项

### 工程与画质

- 固定源码内容指纹与许可证，先核对解析、实际 pass、输出尺寸和采样坐标，再比较画质。
- 测试矩阵：720p/1080p/4K；YUV/RGB；窗口/全屏/最小化；放大/等尺寸/缩小；裁剪/旋转；RIFE 开关；重复切换/恢复；另测 HDR 回退。
- A/B 至少包含：现有高质量传统缩放、你偏好的 stock Anime4K、新候选；保持同帧、同输出尺寸、同 RIFE 与色彩设置，避免默认锐化不一致造成不公平比较。
- 观察线条、纹理、压缩噪声、运动稳定性、字幕。烧录字幕属于视频本身；软字幕/OSD 的实际混合位置另核对，不等同外部屏幕捕获放大整张 UI。

### 性能

- 预热编译与缓存后，采集实际 fresh-frame pass 和播放掉帧/帧节奏。mpv 的 `vo-passes` 原生 node 数据提供 desc/avg/peak/samples，时间单位为纳秒，按 1e6 换算成毫秒；后端未提供时需换有效测量方法。
- 不把“启动墙钟/总帧数”或“pass 数量比”当成 GPU 算法耗时。48fps 约 20.83ms/帧、60fps 约 16.67ms/帧只是输出节奏预算，不是 RIFE 与 shader 可以简单相加的独立预算。
- 本轮不提供确定的毫秒、FPS 或谁比谁快的排名。NIS/SGSR/FSR 的源码可用性只证明路线可信，不证明本机已经跑通或优于现有方案。

### 剩余边界

1. BCAS 全称/版本/算法来源。
2. LS1 原版实现、权重与授权。
3. 各 port 在本机构建和选定 API 下的编译与边界行为；SGSR PARAM、NIS compute 尤需验证。
4. RGB、HDR、字幕组合下的适配，不默认继承游戏 SDK 的颜色域假设。
5. 画质收益与 RIFE 共存的 GPU 余量，均待实际验证。
